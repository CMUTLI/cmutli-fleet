# Add a host to the CMU TLI fleet

Use this guide to install a new fleet host.

The first host in the fleet must be provisioned and installed using the [Fleet
bootstrap](bootstrap.md) procedure.

## Background

A fleet host is a NixOS machine managed from this repository. Common forms
include Campus Cloud VMs, workstations, and public-cloud instances.

Host configuration and service roles live in the `cmutli-fleet` repository. Each
host has its own hardware and disk layout. `modules/base.nix` provides shared
host configuration; service profiles can be added after the machine is
running and reused by hosts serving the same workload.

## Prerequisites

A new host installation requires Nix, Git, SSH, and permission to clone and push
`cmutli-fleet` and `cmutli-fleet-secrets`. Nix is available on Linux and macOS,
and on Windows through WSL2. See [Install Nix](https://nix.dev/install-nix).

A running keys service is required for host enrollment. If this is the first
host and no keys service exists yet, follow [Bootstrap the fleet](bootstrap.md).

### From your computer

Check Git, SSH, and Nix before installing a host:

```console
git --version
ssh -V
nix --extra-experimental-features "nix-command flakes" store info
```

If all three checks pass, skip the troubleshooting below.

---

#### If Nix reports permission denied

Check which group can access the daemon socket (e.g., `nix-users`):

```console
ls -ld /nix/var/nix/daemon-socket
```

Add your user account to the group. Use `sg` to retry the Nix check with that
group, without logging out:

```console
sudo usermod -aG <group-name> "$USER"
sg <group-name> -c 'nix --extra-experimental-features "nix-command flakes" store info'
```

Log out and back in to activate the group membership. To finish this procedure
without logging out, run `newgrp <group-name>` to open a new shell and run
subsequent Nix commands there.

---

## Choose host and service names

Name a fleet host for its primary role or service, then give it the next
two-digit number in that service and environment. If
`www-01.tli.cmu.edu` exists, the next production host is
`www-02.tli.cmu.edu`. Test and development have separate sequences,
starting with `www-t01.tli.cmu.edu` and
`www-d01.tli.cmu.edu`; the letter before the number identifies the
environment. Do not reuse numbers.

Service names omit the host number but reflect the environment:
`www.tli.cmu.edu` for production, `www-test.tli.cmu.edu` for test, and
`www-dev.tli.cmu.edu` for development. Usually, a service name is a CNAME
to one active host. A host can have additional CNAMEs for non-primary
services running on it (e.g., `requests.tli.cmu.edu`). A service can also
span multiple hosts through DNS round robin or an F5 load balancer. Clients
use the service name either way, independent of which hosts serve it.

Choose the host's domain based on its department:

| Department | Domain |
| --- | --- |
| Eberly Center | `eberly.cmu.edu` |
| VPTLI | `tli.cmu.edu` |
| Core Competencies Initiative (CCI) | `core.cmu.edu` |
| Online Education | `online.cmu.edu` |

## Prepare to install

At this point, the new host should show a `nixos@nixos` prompt in the NixOS
live installer. Confirm that before continuing.

### On the installer (console)

Set a password for the installer's `nixos` user:

```console
passwd
```

The installer runs `sshd`, so you can continue from another machine.

### From your computer

Connect to the installer using the host FQDN:

```console
ssh "nixos@<host-fqdn>" # e.g., www-01.tli.cmu.edu
```

### On the installer (SSH)

Record the host's hardware configuration, stable disk IDs, and firmware mode:

```console
nixos-generate-config --show-hardware-config
lsblk -o NAME,SIZE,MODEL,SERIAL
ls -l /dev/disk/by-id
[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS
```

Copy the output. Use another terminal on your computer to edit the fleet
repository while keeping this installer session open.

## Add host to the fleet repository

In `cmutli-fleet`, create the `hosts/<host-fqdn>/` directory for the new host.
You will use the hardware, disk, and firmware information collected in the
previous step to define its system configuration.

### Define hardware

Create the hardware configuration file using the template below.

<samp>hosts/&lt;host-fqdn&gt;/hardware-configuration.nix:</samp>

```nix
{ lib, ... }:

{
  boot.initrd.availableKernelModules = [
    "<module-1>"
    "<module-2>"
  ];

  nixpkgs.hostPlatform = lib.mkDefault "<host-platform>";
}
```

Replace the module names and host platform with the values captured in the
previous step.

For a vSphere VM, also add VMware guest tools inside the module:

```nix
virtualisation.vmware.guest = {
  enable = true;
  headless = true;
};
```

#### Example: `www-01.tli.cmu.edu`

<samp>hosts/www-01.tli.cmu.edu/hardware-configuration.nix:</samp>

```nix
{ lib, ... }:

{
  boot.initrd.availableKernelModules = [
    "ata_piix"
    "vmw_pvscsi"
    "floppy"
    "sd_mod"
    "sr_mod"
  ];

  virtualisation.vmware.guest = {
    enable = true;
    headless = true;
  };

  nixpkgs.hostPlatform = lib.mkDefault "x86_64-linux";
}
```

### Define disks

Disko defines the partitions, filesystems, and mountpoints created during
installation. Disko will erase the disks named in this file, so double-check
their IDs before installing.

Create the disk layout file using the template below. Replace `<os-disk-id>`
with the OS disk's identifier from the `ls -l /dev/disk/by-id` output.

> [!IMPORTANT]
> Use stable `/dev/disk/by-id/` paths, not `/dev/sdX` names. Prefer the `wwn-`
> path when available; it identifies the disk by its worldwide name.

<samp>hosts/&lt;host-fqdn&gt;/disko.nix:</samp>

```nix
{ ... }:

{
  disko.devices.disk.main = {
    device = "/dev/disk/by-id/<os-disk-id>";
    type = "disk";
    content = {
      type = "gpt";
      partitions = {
        bios = {
          size = "1M";
          type = "EF02";
        };
        swap = {
          size = "2G";
          content.type = "swap";
        };
        root = {
          size = "100%";
          content = {
            type = "filesystem";
            format = "ext4";
            mountpoint = "/";
          };
        };
      };
    };
  };
}
```

If the firmware check during [Prepare to install](#prepare-to-install) reported
`UEFI`, replace the entire `bios` entry with this `esp` entry:

```nix
        esp = {
          size = "1G";
          type = "EF00";
          content = {
            type = "filesystem";
            format = "vfat";
            mountpoint = "/boot";
            mountOptions = [ "umask=0077" ];
          };
        };
```

The template reserves 2 GiB of disk swap behind zram, which the CMU TLI fleet
enables by default,
and gives the rest of the disk to root. On a workstation that suspends to disk,
make the disk swap at least as large as RAM; zram
cannot hold a hibernation image.

#### Add any additional disks

Additional disks keep data used by services separate from the OS disk. Choose a
mountpoint for each service by the kind of data it holds:

| Kind of data | Path |
| --- | --- |
| Files served as is, such as static sites and downloads | `/srv/<service-name>` |
| Incoming files waiting to be processed, such as feeds | `/var/spool/<service-name>` |
| State the service owns, such as databases, uploads, and settings | `/var/lib/<service-name>` |

> [!IMPORTANT]
> Use the spool for files awaiting processing; keep processed records in
> `/var/lib/<service-name>`.

**A disk used by only one service** can hold a single filesystem partition mounted
at that service's path. Add `disko.devices.disk.data` after
`disko.devices.disk.main` in the template above. Use the disk's by-id path and
a mountpoint from the table.

<samp>hosts/&lt;host-fqdn&gt;/disko.nix:</samp>

```nix
  disko.devices.disk.data = {
    device = "/dev/disk/by-id/<data-disk-id>";
    type = "disk";
    content = {
      type = "gpt";
      partitions.data = {
        size = "100%";
        content = {
          type = "filesystem";
          format = "ext4";
          mountpoint = "<mountpoint>";
        };
      };
    };
  };
```

**When several services share a disk**, define an LVM volume group on its data
partition and a logical volume for each service at its own mountpoint.
Add `disko.devices.disk.data` and `disko.devices.lvm_vg.data` after
`disko.devices.disk.main` in the template above. Use the disk's by-id path and
set the service names, volume sizes, and mountpoints for the host.

<samp>hosts/&lt;host-fqdn&gt;/disko.nix:</samp>

```nix
  disko.devices.disk.data = {
    device = "/dev/disk/by-id/<data-disk-id>";
    type = "disk";
    content = {
      type = "gpt";
      partitions.data = {
        size = "100%";
        content = {
          type = "lvm_pv";
          vg = "data";
        };
      };
    };
  };

  disko.devices.lvm_vg.data = {
    type = "lvm_vg";
    lvs = {
      "<first-service-name>" = {
        size = "<size>";
        content = {
          type = "filesystem";
          format = "ext4";
          mountpoint = "<first-mountpoint>";
        };
      };
      "<second-service-name>" = {
        size = "<size>";
        content = {
          type = "filesystem";
          format = "ext4";
          mountpoint = "<second-mountpoint>";
        };
      };
    };
  };
```

#### Example: `www-01.tli.cmu.edu`

The `requests` and `ohq` logical volumes each get half of the 100 GiB volume
group.

<samp>hosts/www-01.tli.cmu.edu/disko.nix:</samp>

```nix
{ ... }:

{
  disko.devices = {
    disk = {
      main = {
        device = "/dev/disk/by-id/wwn-0x6000c298bbf47fbcaa3cb57900ebe1bd";
        type = "disk";
        content = {
          type = "gpt";
          partitions = {
            bios = {
              size = "1M";
              type = "EF02";
            };
            swap = {
              size = "2G";
              content.type = "swap";
            };
            root = {
              size = "100%";
              content = {
                type = "filesystem";
                format = "ext4";
                mountpoint = "/";
              };
            };
          };
        };
      };

      services = {
        device = "/dev/disk/by-id/wwn-0x6000c298bbf47fbcaa3cb57900ebe1be";
        type = "disk";
        content = {
          type = "gpt";
          partitions.data = {
            size = "100%";
            content = {
              type = "lvm_pv";
              vg = "services";
            };
          };
        };
      };
    };

    lvm_vg.services = {
      type = "lvm_vg";
      lvs = {
        requests = {
          size = "50%VG";
          content = {
            type = "filesystem";
            format = "ext4";
            mountpoint = "/var/lib/requests";
          };
        };
        ohq = {
          size = "50%VG";
          content = {
            type = "filesystem";
            format = "ext4";
            mountpoint = "/var/lib/ohq";
          };
        };
      };
    };
  };
}
```

> [!TIP]
> You can leave some capacity unallocated so either volume can grow later. To do
> so, give both volumes fixed sizes that leave space in the volume group. See
> [Manage host storage](storage.md) for inspecting and extending
> logical volumes.

### Define configuration

The host configuration sets this machine's hardware, hostname, domain,
bootloader, and NixOS state version. Services to run on the host will be
configured after installation.

Create the host configuration file using the template below.

<samp>hosts/&lt;host-fqdn&gt;/configuration.nix:</samp>

```nix
{ ... }:

{
  imports = [
    ./hardware-configuration.nix
  ];

  boot.loader = {
    grub.enable = true;
  };

  networking.hostName = "<host>";
  networking.domain = "<domain>";

  system.stateVersion = "26.05";
}
```

Replace `<host>` and `<domain>` with those picked from
[Choose host and service names](#choose-host-and-service-names).

If the firmware check during [Prepare to install](#prepare-to-install) reported
`UEFI`, replace the entire `boot.loader` entry with this one.

<samp>hosts/&lt;host-fqdn&gt;/configuration.nix:</samp>

```nix
  boot.loader = {
    systemd-boot.enable = true;
    efi.canTouchEfiVariables = true;
  };
```

#### Example: `www-01.tli.cmu.edu`

<samp>hosts/www-01.tli.cmu.edu/configuration.nix:</samp>

```nix
{ ... }:

{
  imports = [
    ./hardware-configuration.nix
  ];

  boot.loader = {
    grub.enable = true;
  };

  networking.hostName = "www-01";
  networking.domain = "tli.cmu.edu";

  system.stateVersion = "26.05";
}
```

### Add host to the flake

The file `flake.nix` lists every host the fleet can build. Each entry is keyed
by the host's FQDN, because short hostnames repeat across domains (e.g.,
`www-01`). It passes the host's configuration and disk layout to `mkHost`, which
includes the shared host configuration.

Add an entry for the new host among the others, keeping the entries in
alphabetical order.

<samp>flake.nix:</samp>

```nix
nixosConfigurations."<host-fqdn>" = mkHost
  ./hosts/<host-fqdn>/configuration.nix
  ./hosts/<host-fqdn>/disko.nix;
```

#### Example: `www-01.tli.cmu.edu`

<samp>flake.nix:</samp>

```nix
nixosConfigurations."www-01.tli.cmu.edu" = mkHost
  ./hosts/www-01.tli.cmu.edu/configuration.nix
  ./hosts/www-01.tli.cmu.edu/disko.nix;
```

### Stage and check the disk layout

Nix evaluates only files that Git tracks. Stage the new host's files, then
build its disk script without changing the disks:

```console
host_fqdn="<host-fqdn>"
git add flake.nix "hosts/$host_fqdn"
nix --extra-experimental-features "nix-command flakes" build --no-link \
  ".#nixosConfigurations.\"$host_fqdn\".config.system.build.diskoScript"
```

## Partition the host disks

Use the layout in `disko.nix` to create the declared filesystems and
mount them under `/mnt` for installation.

### From your computer

Compare every disk ID in `disko.nix` with the `/dev/disk/by-id` output you
recorded from the installer. This command erases every disk listed in
`disko.nix`, including additional data disks:

```console
host_fqdn="<host-fqdn>"
nix --extra-experimental-features "nix-command flakes" run \
  github:nix-community/nixos-anywhere -- \
  --phases kexec,disko \
  --flake ".#$host_fqdn" "nixos@$host_fqdn"
```

`nixos-anywhere` skips `kexec` when it detects the live NixOS installer.

The filesystems are mounted at `/mnt`. If the installer reboots, repeat the
command with `--disko-mode mount`; repartitioning would erase the host identity
created in the next step.

## Generate the host identity

The host needs an age identity to decrypt its secrets. Generate it on the
prepared disk to keep the private key on the host; use its public key as the
recipient when encrypting secrets for it.

### On the installer (SSH)

Generate the age identity on the mounted disk:

```console
sudo install -d -m 0755 /mnt/var /mnt/var/lib
sudo install -d -m 0700 /mnt/var/lib/sops-age
sudo nix --extra-experimental-features "nix-command flakes" \
  shell github:NixOS/nixpkgs/nixos-26.05#age -c sh -c '
    umask 077
    age-keygen -pq -o /mnt/var/lib/sops-age/identity.txt
    age-keygen -y /mnt/var/lib/sops-age/identity.txt'
```

The final command prints the identity's public key (`age1pq...`), which will be
a recipient of the encrypted `fleet.yaml`. You will need it in the next step.

## Enroll the host identity

Add the host as a recipient of the fleet's encrypted root-password hash.
NixOS decrypts the hash during activation so root login on the console works
on the first boot.

### From your computer

In `cmutli-fleet-secrets`, add the host's recipient to the creation rule in
`.sops.yaml` for `fleet.yaml`. Replace `<host-recipient>` with the public key
from [Generate the host identity](#generate-the-host-identity). Keep all
existing recipients.

If reinstalling a host, replace its old recipient with the new one instead
of adding a second recipient for that host.

<samp>.sops.yaml:</samp>

```yaml
creation_rules:
  - path_regex: ^fleet\.yaml$
    age: <existing-recipients>,<host-recipient>
```

The keys service, `keys.tli.cmu.edu`, will use its own host identity to rewrap
`fleet.yaml`, adding the new host as a recipient.
Commit the updated creation rule and send it to the keys service:

```console
git add .sops.yaml
git commit -m "feat: add <host-fqdn> secret recipients"
git push keys.tli.cmu.edu:cmutli-fleet-secrets +HEAD:refs/heads/incoming
```

### On `keys.tli.cmu.edu` (SSH)

Rewrap `fleet.yaml` to add the new host as a recipient. Review the proposed
recipients when SOPS prompts for confirmation, then commit the rewrapped file.

```console
cd cmutli-fleet-secrets
git checkout -B enroll incoming
SOPS_AGE_KEY_CMD='sudo cat /var/lib/sops-age/identity.txt' \
  sops updatekeys fleet.yaml
git commit -am "chore: rewrap secrets for <host-fqdn>"
```

### From your computer

In `cmutli-fleet-secrets`, fetch and push the rewrapped file:

```console
git fetch keys.tli.cmu.edu:cmutli-fleet-secrets enroll
git merge --ff-only FETCH_HEAD
git push
```

## Check and publish the fleet configuration

The installation must use the secrets revision that includes the new host's
recipient so it can decrypt fleet secrets on first boot. Publish the
configuration to record the host definition and its pinned secrets revision
together in Git.

### From your computer

In `cmutli-fleet`, refresh the pinned secrets input and check every host before
committing and pushing the completed configuration:

```console
host_fqdn="<host-fqdn>"
nix --extra-experimental-features "nix-command flakes" \
  flake update cmutli-fleet-secrets
nix --extra-experimental-features "nix-command flakes" flake check --all-systems
git add flake.nix flake.lock "hosts/$host_fqdn"
git commit -m "feat: add $host_fqdn"
git push
```

## Install NixOS

Install the NixOS system defined by the host's fleet configuration onto the
prepared disks. They already contain the host's age identity, which SOPS uses
on first boot to decrypt fleet secrets in the installed configuration.

### From your computer

Install NixOS onto the mounted disks and reboot into the installed system:

```console
host_fqdn="<host-fqdn>"
nix --extra-experimental-features "nix-command flakes" run \
  github:nix-community/nixos-anywhere -- \
  --phases kexec,install,reboot \
  --flake ".#$host_fqdn" "nixos@$host_fqdn"
```

## Verify the host

Confirm that the installed host has the expected identity and root password
before configuring its base modules.

### From your computer

The installed system has a different SSH host key from the installer. Remove
the installer's entry from `known_hosts`:

```console
ssh-keygen -R "<host-fqdn>"
```

### On the new host (console)

Sign in and read the installed system's SSH host key fingerprint:

```console
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

### From your computer

SSH to the new host and confirm that the fingerprint matches the one shown
on the console. Replace `<username>` with the username of an administrator
defined in the [fleet's user configuration](../modules/users.md):

```console
ssh "<username>@<host-fqdn>"
```

### On the new host (SSH)

Check that the identity's public key matches the value from
[Generate the host identity](#generate-the-host-identity) and that root has
a password. The second command reports `P` when root has a password set.

```console
sudo age-keygen -y /var/lib/sops-age/identity.txt
sudo passwd -S root
```

## Apply service profiles

After host-level setup is complete, add the profiles for the services this
host will provide. A host can import more than one profile. See [Set up a
service](../services/README.md#set-up-a-service) for the profile workflow.
